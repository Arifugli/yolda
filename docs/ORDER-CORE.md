# P0 — ядро заказов и такси

Миграция 011 переименовывает service_requests в orders без копирования строк и сохраняет все UUID/FK, отзывы, сообщения, диспетчеризацию. service_requests — автоматически обновляемое security_invoker-представление для прежнего кода и старого релиза. RLS действует на orders; роли anon/authenticated не получают доступа. Переключение новых заказов на прежний обработчик не требует удаления данных.

## Граница ядра

lib/orders/state.ts — каноническая машина состояний; core.ts — запись состояния и события в той же транзакции. Новые поездки получают engine_version=1, проходят created → searching → offered → accepted → en_route_to_pickup → arrived → in_progress → completed. Отказ до начала возвращает заказ в searching; отмена после начала запрещена. Пропуск этапа, повтор с другим ключом после смены состояния и команды постороннего отклоняются. Прежняя команда finish оставляет канонический in_progress до подтверждения клиентом: awaiting_confirmation — внутренний этап исполнения. Причина отмены сохраняется, финансовые штрафы пока не вводятся.

Для безопасной миграции status/kind в физической таблице пока используют прежние значения; вычисляемые state/service_type дают канонические searching/offered/accepted и ride/freight. Это один источник истины, не два независимых заказа. Поля customer_id/provider_id/data и существующий /api/mobility остаются совместимым API. Выделение универсального публичного API и подключение остальных вертикалей — P1. Вертикаль ride зарегистрирована в lib/orders/verticals.ts; delivery/freight/equipment не объявлены подключёнными к ядру.

Доставка остаётся shipments; грузы/техника сохраняют прежние правила engine_version=0. Общая блокировка занятости между доставкой и поездкой ещё относится к P1. Не запускать открытый многосервисный пилот до этой проверки.

## Тариф и rollout

order_tariffs хранит активный тариф economy с версией и валидируемыми параметрами base/perKm/minimum/roundTo/maxKm. Цена проверяется сервером и целиком сохраняется в price_snapshot (правила, версия, UZS, расстояние). Изменение тарифа не меняет существующие заказы. Новый UI отправляет quotedTariffVersion; прежние клиенты остаются совместимыми по проверке суммы. Админский редактор тарифов — следующий этап. Денежные расчёты остаются демонстрационными, расстояние — по прямой.

ORDER_CORE_ENABLED=false отключает ядро только для новых поездок. Существующие поездки v1 продолжают его использовать. Старые строки получают version=0; массового изменения статусов активных заказов нет. Перед релизом — резервная копия БД; проверка на staging. Миграция использует краткую DDL-блокировку, поэтому для большой базы нужен отдельный релизный слот. Не удалять orders при rollback: отключить новые v1 поездки флагом на текущем образе. Старый образ не знает этап en_route_to_pickup и не ведёт core-events: откат к нему допустим только после завершения v1 заказов и отдельной проверки совместимости.

## SMS

Без настроек остаётся явно защищённая демоверсия. Адаптер lib/sms.ts поддерживает Eskiz: SMS_PROVIDER=eskiz, ESKIZ_TOKEN, ESKIZ_TEMPLATE с {code}, необязательный ESKIZ_SENDER (по умолчанию 4546). Токен и одобренный шаблон задаются только в секретах хостинга. Ответ SMS-режима не содержит код; ошибка провайдера не раскрывает ответ/токен/телефон, демо-fallback отсутствует. Вход принимает код только от текущего провайдера; ранее выданный demo-код после переключения не подходит. OTP хранится как HMAC, имеет TTL и лимит попыток.

Контракт адаптера проверен на подставном HTTP-ответе. Настоящий аккаунт Eskiz, одобрение шаблона, доставка SMS, обновление истёкшего токена и провайдерские лимиты требуют проверки перед включением. Отправка пока синхронная с 10-секундным timeout; надёжная очередь внешних операций — P1. Это не подключение MyID/проверки документов, эквайринга или дорожного провайдера.

## Демо и ручная приёмка

1. Войти отправителем: на главной карта, четыре услуги, адреса и заказы в прокручиваемой нижней панели. Проверить 390×844 и отказ GPS.
2. В аккаунте водителя включить онлайн с машиной и геопозицией. Заказать поездку A→B; проверить цену до подтверждения.
3. Принять поездку → «Еду к заказчику» → «Я прибыл» → получить код у клиента → начать → сообщить о выполнении → клиент завершает и оставляет отзыв через детали.
4. Отменить другую поездку до начала. Повторить запрос после потери ответа: один заказ, один переход.
5. Проверить прежнюю доставку и кран: их сценарии сохранены.

Карты остаются Leaflet/OSM с явным поиском Nominatim; ключей Yandex и коммерческой лицензии нет. Автодополнение, дорожный ETA, реальный SMS и замеры Lighthouse/Android не объявляются выполненными. Главная теперь загружает карту по требованию компонента: это требует отдельного измерения производительности до заявления <2 секунд.
