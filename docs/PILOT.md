# Эксплуатация и переход к пилоту

## Честный статус

Это работающая демонстрационная версия с сервером и PostgreSQL, а не разрешение на production. Реальные перевозки, биометрическая проверка и финансовые операции пока не подключены. Этап 2 не реализован. Нельзя публиковать открытое демо с административными вымышленными аккаунтами и известными локальными паролями как боевой сервис.

## Что подтвердить перед закрытым пилотом

1. **Модель работы и Узбекистан.** С местными юридическими и финансовыми специалистами подтвердить основание/согласие на обработку данных, требования к их размещению, срокам хранения и трансграничной передаче, правила перевозки/запрещенные категории, договоры с отправителем и попутчиком, ответственность за утрату/повреждение, порядок споров, налоги и возможность расчетов/выплат физическим лицам. Проверку соответствия законодательству этот проект не проводил и не заявляет.
2. **MyID.** Заключить договор, получить актуальную официальную документацию и доступ к тестовой среде. Подтвердить server-side способ получения результата, аутентификацию и подлинность уведомлений, связь проверки с конкретным пользователем, возраст, перечень минимальных атрибутов, повторную проверку и сроки хранения. Реализовать отдельный адаптер MyID, контрактные тесты ошибок/повторов/подписей. OneID и MyGov не являются заменой MyID.
3. **Регистрация/SMS.** Подключить подтвержденного провайдера SMS, убрать отображение кодов, включить IP/device-лимиты у доверенного gateway, защиту от массовой регистрации и мониторинг злоупотреблений. Демо-проверка возраста использует дату регистрации и не является удостоверением личности.
4. **Платежи.** Выбрать провайдера с документированным приемом платежей, возвратами и допустимым способом вознаграждения курьеров. Не включать hold/split/payout, если они не подтверждены договором и API. Проверять подпись raw-body уведомления, привязку суммы/валюты/заказа, уникальный event/reference и сверку с API провайдера. Включить outbox/очередь с retries, reconciliation и финансовым аудитом. Раздельно протестировать refund и payout. До этого реальные деньги отключены.
5. **Инфраструктура.** Разместить PostgreSQL и приватное S3 в подтвержденном регионе, заменить все локальные demo-значения, настроить TLS, IAM с минимальными правами, сетевую изоляцию, шифрование резервных копий, WAF/rate limiting и сбор обезличенных ошибок. S3rver допустим только локально; открыть его в production нельзя. За reverse proxy задать APP_ORIGIN и обеспечить корректный HTTPS/Secure-cookie.
6. **Карта и зоны.** Подключить лицензированный картографический/маршрутный провайдер, геокодирование, точные полигоны зоны и дорожную оценку времени. Сейчас расстояния по прямой и дополнительное время — явно приблизительные эвристики, а не SLA. Проверить транспорт/габариты и безопасные места встреч.
7. **UX и локализация.** Завершить узбекские тексты, юридические согласия, доступность, публичный экран отслеживания, установку PWA/иконки разных размеров, управление аккаунтом/удалением, просмотр и модерацию отзывов, подробные рабочие инструкции поддержки. Протестировать на реальных iOS/Android браузерах. Автоматизация Chromium не заменяет device testing.
8. **Операции.** Настроить сроки хранения/возврата, правила подтверждения в пункте, права назначенных сотрудников, аварийный сценарий при неисправности постамата, отказе получателя или потере посылки. Return-flow сейчас моделирует код отправителя; реальные возвраты из неисправных/истекших ячеек требуют сотрудника и отдельного оборудования/протокола. Провести учения до перевозки реальных вещей.
9. **Приемка.** Независимая проверка безопасности, нагрузочный тест SSE/БД, восстановление backups, документация об инцидентах, тесты поддельных и повторных событий реальных провайдеров. Запустить малую группу в одном городе с поддержкой, наблюдать реальные метрики и только потом расширять.

## Политика данных для демо и предлагаемые пилотные сроки

Демо хранит исключительно вымышленные данные. Не загружайте реальные документы/биометрию. Личность: только результат, reference и время; паспортные сканы отсутствуют. Фотографии очищаются от метаданных и выдаются только владельцу/участнику заказа, доказательства также — аудируемой поддержке. Service worker не кеширует заказы или фото. Имена/адреса/коды/токены не выводятся сервером в журнал ошибок.

OTP действуют пять минут, сессии семь дней. Просроченные OTP, сессии и счетчики запросов можно удалять ежедневным maintenance. Не удаляйте доказательства открытого спора. Предлагаемые сроки до юридического подтверждения: геолокацию удалить при завершении, фото закрытых бесспорных заказов через 30 дней, чат через 90 дней, операционную историю/аудит по утвержденному регламенту; финансовые документы — только после согласования обязательных сроков. Автоматическое удаление заказов/финансовых записей сейчас не включено.

При запросе удаления аккаунта поддержка сначала разрешает активные доставки/споры и обязательства. Далее удаляет приватные объекты и псевдонимизирует профиль, сохраняя только обоснованную историю/обязательные документы. Для production нужен проверенный автоматизированный процесс и доказуемое удаление из backups по согласованной политике; текущая версия его не заявляет.

## Резервное копирование и восстановление

Из корня репозитория с запущенным контейнером PostgreSQL:

```bash
mkdir -p backups
# Каталог backups нужно хранить вне Git и шифровать на реальном сервере.
docker compose exec -T db pg_dump -U yolda -Fc yolda > backups/yolda.dump
sha256sum backups/yolda.dump > backups/yolda.dump.sha256
# Фотографии находятся в S3, их версия/копия должна соответствовать этому моменту БД.
# Для Compose-эмулятора: объектный том экспортируется отдельно.
docker compose cp storage:/app/storage/objects backups/objects
```

Восстанавливайте сначала **в новую изолированную базу**, не поверх работающего сервиса:

```bash
sha256sum -c backups/yolda.dump.sha256
docker compose exec -T db createdb -U yolda yolda_restore
cat backups/yolda.dump | docker compose exec -T db pg_restore -U yolda --exit-on-error --no-owner -d yolda_restore
# Проверка схемы, количества записей и связей:
docker compose exec -T db psql -U yolda -d yolda_restore -c 'SELECT count(*) FROM shipments;'
```

Затем восстановите приватное объектное хранилище из версии/копии, подключите приложение к новой базе и проверьте чтение фото/карточек и полный тестовый цикл. Перед переключением проверяются контрольные суммы, схема, число объектов, бизнес-инварианты и доступ только авторизованным пользователям. Старую базу сохраняйте до приемки; при восстановлении не переносите живые сессии в публичную среду без ревокации.

Production: ежедневные зашифрованные backups, PostgreSQL WAL/PITR, версии S3-объектов, отдельно ключи расшифрования, периодические restore drills. RPO/RTO утверждаются оператором сервиса; здесь они не обещаются.

## Формулы административных метрик

Все числа получаются из PostgreSQL; пустой знаменатель показывается «—».

- Опубликованные: число заказов в текущем published; завершенные: текущий completed.
- Доля с курьером: заказы с ненулевым courier_id / все заказы кроме черновиков. Это текущая доля, не когортная метрика.
- Время назначения: среднее (Assignment.created_at − Shipment.created_at) в минутах; включает время подготовки черновика. Для полноценной операционной аналитики отдельно измеряйте published_at → assigned_at.
- Вовремя: среднее (первое событие received ≤ согласованное deliverBy) среди завершенных заказов.
- Отмены: число cancelled; причины смотрите в ленте/аудите; классифицированная агрегация причин еще не реализована.
- Споры: заказы с открытым спором.
- Повторные отправители: число пользователей с более чем одним completed заказом.
- Активные курьеры: уникальные courier_id в assigned/picked_up/in_transit/awaiting_receipt.
- Объем оплат: сумма записей Payment со статусом paid. Комиссии: сумма зафиксированных fee по заказам payment_status=paid. Возвраты: сумма Refund со статусом refunded.

Набор включает демонстрационные операции, если база демонстрационная. В интерфейсе это подписано. На production нужны фильтр периода, исключение demo, сверка учета и согласованные определения финансовых показателей.

Демо-эмулятор S3 изолирован на loopback, требует подписанных запросов и включается только для разработки. Его устаревшие транзитивные зависимости имеют четыре известные advisory (три high, одна moderate); это дополнительная причина исключить эмулятор из production. Production-зависимости приложения проверены отдельно через `npm audit --omit=dev` — advisory не обнаружены на момент проверки. Это не заменяет аудит безопасности.

Повторяемые ответы API с кодами/приглашениями шифруются AES-256-GCM и привязываются к пользователю, действию и ключу. В demo случайный ключ создается в `storage/.response-key` с правами 0600; файл находится вне Git. В production обязателен защищенно переданный `APP_ENCRYPTION_KEY` (32-байтный hex), без него операции не получают демонстрационный ключ. Резервное копирование этого ключа отдельно от базы необходимо для чтения replay-ответов; потеря ключа не удаляет заказы, но нарушает их воспроизведение по прежнему Idempotency-Key. Не выводите ключ в логи или чат.
