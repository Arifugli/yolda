# API v0

Базовый путь `/api`. JSON UTF-8, суммы — целые сумы, даты ISO 8601 в UTC. Сессия — HttpOnly-cookie `yolda_session`, SameSite=Lax; на HTTPS ставится Secure. POST из другого Origin или Sec-Fetch-Site=cross-site отклоняется. За reverse proxy задайте `APP_ORIGIN` и очищайте недоверенные forwarded-заголовки.

Доменные POST требуют уникальный `Idempotency-Key` (до 100 символов). Frontend сохраняет ключ при сетевом сбое до получения подтвержденного ответа. Повтор ключа возвращает сохраненный результат; ключ, использованный для другого действия/заказа, дает 409. В реальном мобильном приложении потребуется отдельный документированный токеновый auth transport; доменные маршруты и права уже вынесены из UI.

Ошибка: `{ "error": "сообщение", "fields": [...] }`; поля бывают при валидации. HTTP: 400 поля, 401 сессия, 403 права, 404 ресурс, 409 конфликт/этап, 413 размер, 429 лимит, 500 ошибка зависимостей. Неверный код передачи возвращает `{error,attemptsRemaining}` с сохраненным счетчиком; HTTP-клиент должен проверять поле error и не считать 200 подтверждением передачи.

## Вход и профиль

| Метод/путь | Данные/назначение |
|---|---|
| POST auth/otp | `{phone,name,dob}`. Телефон `+998` + 9 цифр. В demo возвращает код симуляции, в production отключен |
| POST auth/login | `{phone,code}`, расходует OTP и устанавливает сессию |
| POST auth/logout | удаляет сессию |
| GET config | публичные настройки сервиса, без персональных данных и секретов |
| GET me | свой профиль, настройки, статистика, опубликованные рейтинги |
| POST verify | явно демонстрационная проверка взрослого пользователя, только сервер присваивает verified |
| POST profile | `{transport:walk|bike|car,city,accepting,language:ru|uz,notifications,avatarId?}` |
| GET couriers | публичные данные принимающих заказы проверенных пользователей |
| POST/GET route | `{origin:[lat,lng],destination:[lat,lng],departAt,city}` / сохраненная поездка |
| GET nearby | `?city=&lat=&lng=&destLat=&destLng=`. Только приблизительные районы и условия; точных адресов/контактов нет |

## Заказы

POST `shipments` создает **черновик**, не публикует. Пример тела:

```json
{
  "origin": {"kind":"person","city":"Фергана","district":"Центр","address":"Вымышленная улица, 10","lat":40.386,"lng":71.786},
  "destination": {"kind":"person","city":"Фергана","district":"Университет","address":"Вымышленная улица, 22","lat":40.4,"lng":71.8},
  "recipient":"+998900000002",
  "category":"Документы",
  "description":"Упакованные документы",
  "weight":1,
  "dimensions":[20,15,10],
  "declaredValue":50000,
  "fragile":false,
  "pickupAt":"2030-01-01T05:00:00Z",
  "deliverBy":"2030-01-01T08:00:00Z",
  "instruction":"Вход со двора",
  "payer":"sender",
  "allowedContents":true,
  "packaging":true,
  "urgent":false,
  "photos":[]
}
```

Возвращает `{id,invite}`. Получатель `recipient` может быть телефоном или публичным ID. Для point/locker добавляется `lockerId` из GET `lockers`; тип и город сверяются с записью точки. В текущем MVP города двух точек должны совпадать. Зона сервиса задается кругом (центр + радиус) для каждого выбранного города в settings.zones. Координаты точек проверяются сервером. Для point/locker используются серверные координаты/адрес каталога. Точные геополигоны требуют реализации до пилота.

GET `shipments` — собственные заказы, GET `shipments/:id` — карточка участника с событиями, сообщениями, откликами и доказательствами спора. Постороннему подробности не возвращаются. Действия: POST `shipments/:id/:action`.

| Action | Кто / тело |
|---|---|
| publish | проверенный отправитель |
| consent | получатель-плательщик, согласие оплатить |
| pay | проверенный плательщик; только demo, идемпотентная операция по заказу |
| offer | проверенный потенциальный курьер, прием заказов включен; нельзя быть отправителем/получателем |
| assign | отправитель, `{courierId}`; только из откликов и после оплаты |
| arrive, transit, destination, ready | назначенный курьер; последовательность этапов обязательна |
| code | отправитель/получатель, `{stage:pickup|delivery|return}`; возвращает код на 5 минут |
| handover | назначенный курьер, `{stage,code}`; только для передачи человеком |
| complete | проверенный получатель после received |
| cancel | отправитель до забора; оплата становится refund_pending |
| decline | курьер до забора; заказ снова опубликован |
| failure | курьер, `{reason}`, ответственность сохраняется |
| return | отправитель согласует возврат после забора |
| returning | курьер после return_agreed; прием отправителем через return-code |
| invite | отправитель перевыпускает приглашение для еще не привязанного получателя |
| tracking.link | отправитель, создает секретный токен публичного статуса |
| message | `{text,photoId?}`; максимум 20/мин, только участники |
| report | `{messageId,reason}`; жалоба на сообщение этого заказа |
| location | активный курьер, `{lat,lng,consent:true}` |
| dispute | участник, `{reason,evidence?:fileUUID[]}`; блокирует невыплаченное начисление |
| review | участник после завершения/возврата, `{targetId,role,stars,comment,reason}`; role sender/courier/recipient, reason punctuality/communication/packaging/care |
| locker | `{operation:reserve|deposit|collect|expire|reclaim,endpoint:origin|destination,eventId}`. reclaim возвращает исходную посылку отправителю до забора курьером. Отдельные разрешения по роли и этапу, проверка связи/двери/размеров/срока; point возвращает pendingOperator для физического действия |

POST `claim` с `{invite}` — проверенный получатель принимает секретное приглашение. GET `tracking/:token` без сессии возвращает только `{status,updated_at}`. GET `events?shipmentId=...` — авторизованный SSE с карточкой; авторизация повторяется при каждом обновлении. Соединение закрывается примерно через минуту и EventSource реконнектится. После завершения координаты больше не выдаются в карточке.

## Фотографии и учет

POST `files` — multipart `file` и необязательный `shipmentId`; проверяет принадлежность заказу, заголовок/декодирование изображения, размер. Возвращает UUID. GET `avatars/:userId` — только явно назначенное владельцем фото публичного профиля для зарегистрированных пользователей. Фото заказа нельзя назначить аватаром. GET `files/:id` — фото владельца или участника связанного заказа, Cache-Control private/no-store. Доказательства видны поддержке через отдельный аудируемый `admin/files/:id`, не через публичную ссылку.

GET `income`, `notifications`, `lockers` — начисления пользователя, его уведомления и публичный каталог демонстрационных точек.

## Администрирование

GET `admin` возвращает данные согласно роли. Оператор получает только свои пункты и ожидающие подтверждения операции; финансовый сотрудник — учет, поддержка — споры/жалобы, admin — все.

- POST `admin.settings`: полная JSON-конфигурация имени, городов, лимитов, запрещенных категорий и тарифа; admin.
- POST `admin.user`: `{id,restricted}`, admin.
- POST `admin.locker`: `{id,connected,fault:none|door|full}`, admin, управляет симуляцией сбоя.
- POST `admin/point.confirm`: `{requestId}`, назначенный оператор или admin, подтверждает прием/выдачу.
- POST `admin/resolve`: `{shipmentId,resolution}`, admin, решение спора.
- POST `admin/payout`, `admin/refund`: `{shipmentId}`, finance/admin; только demo, физические деньги не двигаются.
- POST `admin/moderate`: `{reportId,hide}`, support/admin; скрывает сообщение, разрешает жалобу, сохраняет аудит.

Реальные payment/MyID webhooks **не принимаются**: их протоколы, подписи и доступ еще не подтверждены. Нельзя отправить client-status и получить оплату или проверенную личность. Дедупликация демо-оплаты обеспечивается отдельным provider_ref и ограничениями базы; до включения реального провайдера нужны тесты на его документированные подписи и replay protection.
# Такси, грузоперевозки и спецтехника

Все маршруты ниже требуют сессии Yolda, POST также требуют Idempotency-Key и допустимый Origin.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/mobility?kind=taxi\|cargo\|equipment&view=mine\|market\|support` | Свои заявки/отклики, обезличенный поиск, споры для support/admin |
| POST | `/api/mobility` | Заявка; для такси сервер сверяет координаты/цену и запускает автоподбор |
| GET | `/api/mobility/:id` | Карточка с доступом по участию; посторонний видит только обезличенную опубликованную заявку |
| GET/POST | `/api/mobility/vehicles` | Собственные машины, регистрация/обновление с декларацией разрешений |
| GET/POST | `/api/mobility/presence` | Свой статус/входящие поездки; GPS heartbeat с согласием или удаление позиции при offline |
| POST | `/api/mobility/quote` | Прозрачная фиксированная демо-цена такси по координатам |
| POST | `/api/mobility/:id/dispatch` | Продолжение автопоиска заказчиком; подбор также вызывается при публикации и heartbeat водителя |
| POST | `/api/mobility/:id/accept` | Принятие такси водителем в пределах 45 секунд |
| POST | `/api/mobility/:id/offer`, `/assign`, `/withdraw` | Предложение/выбор/отзыв для грузов и техники; ручное назначение такси запрещено |
| POST | `/api/mobility/:id/arrive`, `/code`, `/start`, `/finish`, `/complete` | Выполнение с кодом начала и отдельным подтверждением заказчика |
| POST | `/api/mobility/:id/cancel`, `/decline` | Отмена заказчиком/отказ исполнителя до начала |
| POST | `/api/mobility/:id/message`, `/dispute`, `/resolve`, `/review` | Чат участников, спор, решение support/admin, взаимные отзывы |

Модели входных данных: `lib/mobility-schema.ts`. Подробные ограничения и параметры автопоиска: [SUPABASE.md](SUPABASE.md). Денежные операции новых услуг не симулируются как успешные платежи: хранится только согласованная цена.

## Мобильное оформление

- `GET /api/places?q=...&lat=...&lng=...` — явный поиск адреса; `GET /api/places?mode=reverse&lat=...&lng=...` — адрес точки. Требуется сессия, лимит 30 запросов/минуту на пользователя. Возвращаются проверенные данные геокодера, без выдуманных адресов при ошибке.
- `POST /api/delivery.quote` — стоимость короткой доставки (`origin`, `destination`, `parcel: small|medium|large`).
- `POST /api/delivery.book` — атомарное оформление с тем же маршрутом, телефоном `recipient`, `quotedPrice`, описанием и явными `allowedContents=true`, `packaging=true`. Сервер применяет прежние проверки личности, зон и посылки. В демо создаёт одну оплату и запускает поиск; первый допустимый отклик автоматически назначается. Ключ идемпотентности обязателен.
- Короткие доставки ожидающему регистрации получателю автоматически привязываются после OTP-входа по указанному номеру. Связь с чужим номером по приглашению запрещена; обычные подробные отправления сохраняют прежний порядок.

Простой заказ такси использует существующие `/api/mobility/quote` и `POST /api/mobility`, но клиент скрывает публикации, фиксирует время запроса для повторов и запускает поездку одной кнопкой. Геопозиция водителя и подтверждение поездки сохранены. [Описание интерфейса](MOBILE.md).

## P1 — автоматическая доставка и поток Order

- `POST /api/delivery/presence`: `{online:false}` либо `{online:true,transport,lat,lng,accuracy,consent:true}`; транспорт walk/bike/scooter/car должен совпадать с профилем. Требуются приём заказов и проверенная личность.
- `GET /api/delivery/presence`: входящие предложения текущего курьера (маршрут, цена, expires_at), без телефона получателя.
- `POST /api/delivery/:id/accept|reject`: ответ назначенного кандидата; все POST используют прежний Idempotency-Key.
- `POST /api/delivery/:id/dispatch`: дополнительный запрос поиска владельцем. Основной поиск выполняет worker без клиентских запросов.
- `POST /api/shipments/:id/depart`: выезд назначенного курьера в новой доставке; затем прежние arrive/code/handover/transit/destination/ready/complete.
- `GET /api/orders/:id/events`: авторизованный SSE со снимком состояния, ревизией сообщений и свежей позицией исполнителя. Переподключение восстанавливает текущее состояние. Старые доставки без Order используют прежний API/поток.

Подробности совместимости и лимитов: [DISPATCH.md](DISPATCH.md).

## Грузовые услуги и спецтехника

`mobility/quote`, `create`, `presence` поддерживают cargo/equipment и matchingMode; контракт и примеры параметров — [HEAVY-ORDERS.md](HEAVY-ORDERS.md). Старые запросы без режима остаются ручными предложениями, новые заказы получают Order v1.
